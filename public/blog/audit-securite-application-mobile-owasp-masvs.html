Audit de sécurité d’une application mobile : ce que couvre l’OWASP MASVS

Votre application manipule des comptes, des paiements ou des données personnelles ? Voici, sans jargon inutile, ce que vérifie un audit de sécurité mobile sérieux et comment le lire.

Publié le 26 novembre 2026 · par l’équipe ITBerg

MASVS, MASTG, MobSF : qui fait quoi

Trois noms reviennent dans tout audit de sécurité mobile. Ils sont complémentaires :

  • OWASP MASVS (Mobile Application Security Verification Standard) : la liste de ce qu’une application doit garantir. C’est le « quoi ».
  • OWASP MASTG (Mobile Application Security Testing Guide) : la façon de le vérifier, test par test, sur Android et iOS. C’est le « comment ».
  • MobSF (Mobile Security Framework) : un outil open source qui analyse automatiquement un APK, un AAB ou un IPA. C’est un accélérateur, pas un verdict.

Ce sont des référentiels et des outils publics. Un prestataire qui s’en sert ne « certifie » pas votre application : il vérifie, preuves à l’appui, et vous dit ce qu’il faut corriger.

Les domaines vérifiés

Le MASVS regroupe les exigences en grands domaines. Les voici, traduits en questions simples :

  • STORAGEStockage : un jeton, un mot de passe ou une donnée personnelle reste-t-il lisible sur le téléphone, dans les journaux ou les sauvegardes ?
  • CRYPTOCryptographie : les algorithmes sont-ils à jour, les clés sont-elles dans le Keystore ou le Keychain plutôt que dans le code ?
  • AUTHAuthentification : la session expire-t-elle, la biométrie protège-t-elle vraiment quelque chose côté serveur ?
  • NETWORKRéseau : tout passe-t-il en HTTPS avec des certificats vérifiés ?
  • PLATFORMPlateforme : composants exportés, liens profonds, WebView : qu’est-ce qu’une autre application peut déclencher ?
  • CODECode : les bibliothèques sont-elles à jour, les entrées sont-elles contrôlées ?
  • RESILIENCERésilience : l’application résiste-t-elle à la modification et à l’analyse, quand c’est nécessaire ?
  • PRIVACYVie privée : la collecte est-elle limitée au nécessaire et expliquée à l’utilisateur ?

Toutes les applications n’ont pas besoin du même niveau. Une application vitrine se contente des contrôles de base (souvent appelés L1). Une application de santé ou de finance vise un niveau renforcé (L2). La résistance à la rétro-ingénierie (R) se justifie surtout quand l’application protège un modèle économique ou un contenu payant.

Le déroulé d’un audit

  1. Cadrage et autorisation écrite

    Périmètre, niveau visé, comptes de test, environnement. On ne teste jamais une application sans l’accord écrit de son propriétaire.

  2. Analyse automatisée

    MobSF et outils complémentaires sur le fichier de l’application : permissions, secrets laissés dans le code, configuration réseau, bibliothèques vulnérables.

  3. Tri manuel

    Chaque alerte est vérifiée à la main. Un scanner produit beaucoup de faux positifs, et manque ce qui dépend de la logique métier.

  4. Tests manuels et intrusion

    Interception du trafic, rejeu de requêtes vers l’API, tentative d’accès aux données d’un autre utilisateur, contournements côté client.

  5. Rapport et contre-audit

    Chaque faille avec sa gravité, sa preuve, son impact et la correction recommandée, puis une vérification des corrections.

Ce que l’on oublie souvent : le backend

Une application n’est sûre que si son serveur l’est aussi. Beaucoup de problèmes ne se voient pas dans l’APK : des règles Firebase trop ouvertes, une API qui renvoie les données d’un autre compte si l’on change un identifiant, une clé d’API sans restriction. Un audit sérieux suit les requêtes jusqu’au serveur et s’appuie aussi sur le Top 10 OWASP des API.

Et si l’application contient de l’IA ?

Un assistant ou un agent intégré à l’application ouvre de nouvelles portes : injection de prompt, fuite d’instructions ou de documents, actions excessives. Nous les testons en nous appuyant sur le Top 10 OWASP pour les applications LLM. Voir notre article sur les agents IA sous contrôle.

Comment lire un rapport d’audit

  • Commencez par la synthèse : elle doit être compréhensible sans connaître le MASVS.
  • Traitez d’abord les failles critiques et élevées, celles qui exposent des données ou des comptes.
  • Pour chaque correction, demandez un contre-test : une faille n’est fermée que quand on a vérifié qu’elle l’est.
  • Ajoutez des analyses automatiques à votre intégration continue pour que la même faille ne revienne pas.
