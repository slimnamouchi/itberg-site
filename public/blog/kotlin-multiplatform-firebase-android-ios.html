Kotlin Multiplatform et Firebase : une appli Android et iOS, un seul code métier

Faut-il vraiment écrire deux applications, une pour Android et une pour iOS ? Avec Kotlin Multiplatform, on partage le code qui compte (les règles métier, les données, parfois les écrans) et on garde le natif là où il est utile. Voici comment nous l’associons à Firebase, et les pièges que nous avons appris à éviter.

Publié le 26 novembre 2026 · par l’équipe ITBerg

Le principe : partager ce qui ne dépend pas de l’écran

Une application mobile, c’est en réalité plusieurs couches. Il y a ce que l’utilisateur voit (les écrans), ce que l’application sait faire (les règles métier : calculer un panier, valider un formulaire, décider quoi afficher hors connexion), et ce qui la relie au monde (le réseau, la base locale, les services comme Firebase). Écrire deux applications natives séparées, c’est écrire tout cela deux fois, puis corriger chaque bug deux fois.

Kotlin Multiplatform (KMP), la technologie de JetBrains, permet d’écrire une seule fois le code qui ne dépend pas de la plateforme, en Kotlin, et de le compiler pour Android (comme d’habitude) et pour iOS (en code natif). Elle est déclarée stable depuis fin 2023. Compose Multiplatform va plus loin et permet aussi de partager les écrans ; sa version iOS est stable depuis 2025.

Ce n’est pas du « tout ou rien ». On peut partager seulement le métier et garder des écrans natifs (Jetpack Compose sur Android, SwiftUI sur iOS), ou tout partager. C’est l’une des grandes différences avec des solutions comme Flutter ou React Native, qui imposent leur propre façon de dessiner l’interface.

Ce que nous partageons, et ce que nous gardons par plateforme

Sur nos propres applications, El9offa et EasyFind, la règle est la même :

  • Toujours partagé : le domaine métier, en Kotlin pur, sans aucune dépendance à Android, à iOS ni à Firebase. C’est là que vivent les règles importantes, et c’est la partie la plus facile à tester.
  • Partagé le plus souvent : les données. Réseau (Ktor), sérialisation (kotlinx.serialization), dates (kotlinx-datetime) et base locale : la bibliothèque Room de Google fonctionne désormais aussi en Kotlin Multiplatform, tout comme SQLDelight.
  • Partagé selon le projet : les écrans, avec Compose Multiplatform. Très rentable pour une petite équipe ; moins pertinent si l’application doit coller au millimètre aux conventions visuelles d’iOS.
  • Gardé par plateforme : ce qui touche au système (notifications, paiement intégré, widgets, certaines autorisations), via le mécanisme expect/actual ou une simple interface implémentée de chaque côté.

Brancher Firebase dans une application multiplateforme

Firebase est très pratique pour une application mobile : connexion des utilisateurs (Authentication), base de données synchronisée (Firestore), fonctions côté serveur (Cloud Functions), notifications (FCM), réglages à distance (Remote Config), hébergement de fichiers statiques (Hosting). Ses kits de développement officiels sont pensés pour chaque plateforme. Pour les utiliser depuis du code Kotlin partagé, il y a deux approches :

1. Une bibliothèque Kotlin Multiplatform pour Firebase

La bibliothèque open source de GitLive enveloppe les SDK officiels Android et iOS derrière une seule API Kotlin. On écrit l’accès à Firestore ou à l’authentification une seule fois. C’est rapide, mais on dépend d’un projet communautaire pour suivre les évolutions de Firebase. Au moment de démarrer, vérifiez aussi où en est le support officiel de Google : il évolue.

2. Firebase derrière une interface, implémentée par plateforme

Le code partagé ne parle qu’à une interface à vous (« enregistrer une liste », « récupérer l’utilisateur connecté »). Chaque plateforme l’implémente avec le SDK officiel. Un peu plus de code, mais le domaine ne sait même pas que Firebase existe : on peut le tester sans réseau, et changer de backend plus tard sans toucher aux règles métier.

Nous combinons souvent les deux : une bibliothèque multiplateforme pour aller vite, mais toujours derrière une interface, pour que le domaine reste indépendant.

Les pièges que nous voyons le plus souvent

  • Oublier le hors-connexion. En Tunisie comme ailleurs, la connexion n’est pas toujours bonne. L’écran doit lire une base locale, et la synchronisation la mettre à jour, plutôt que d’attendre le réseau à chaque affichage.
  • Laisser le domaine dépendre de Firebase. Si les règles métier manipulent directement des documents Firestore, tout devient difficile à tester et impossible à migrer.
  • Négliger les règles de sécurité. Avec Firebase, l’application parle directement à la base : ce sont les règles Firestore et Storage qui empêchent un utilisateur de lire les données d’un autre. Elles se testent sur l’émulateur, à chaque modification, comme du code.
  • Un seul environnement. Un projet Firebase de développement et un de production, séparés. Rien n’arrive en production sans un accord explicite.
  • Oublier le coût. Lectures Firestore, SMS de vérification, fonctions planifiées : chaque fonction coûteuse mérite un interrupteur à distance (Remote Config) et un comportement sûr par défaut.
  • Sous-estimer iOS. Compiler pour iOS demande un Mac avec Xcode, un compte développeur Apple, et un peu de temps pour la publication sur l’App Store. À prévoir dans le planning dès le début.

Quand ne pas choisir Kotlin Multiplatform

KMP n’est pas toujours la bonne réponse :

  • si l’application est surtout de l’affichage, avec très peu de logique, une seule base de code d’interface (ou même un site web bien fait) peut suffire ;
  • si votre équipe est déjà experte en Flutter ou en Swift et n’a pas de Kotlin, le coût de la transition peut dépasser le gain ;
  • si vous ne visez qu’Android pour longtemps, une application Android classique reste plus simple. La bonne nouvelle : une architecture propre, avec un domaine en Kotlin pur, se migre ensuite vers KMP sans tout réécrire.

Par où commencer

  1. Écrire le domaine d’abord

    Les règles métier en Kotlin pur, avec leurs tests unitaires, avant le moindre écran ou appel réseau.

  2. Choisir le niveau de partage

    Métier seul, métier et données, ou aussi les écrans : on décide selon l’équipe et l’exigence visuelle sur iOS.

  3. Poser Firebase derrière des interfaces

    Deux projets (développement et production), des règles de sécurité testées sur émulateur, des interrupteurs à distance.

  4. Automatiser les contrôles

    Une intégration continue qui vérifie le style (ktlint, detekt), lance les tests et compile Android et iOS à chaque pull request.
