Agent IA avec LangGraph : garder un humain aux commandes

Un agent IA qui agit seul fait peur, à juste titre. Avec LangGraph, on peut écrire le chemin qu’il suit et l’arrêter là où une personne doit décider. Voici la méthode que nous appliquons.

Publié le 26 novembre 2026 · par l’équipe ITBerg

Pourquoi un agent a besoin d’un cadre

Un agent IA enchaîne plusieurs étapes : lire une demande, chercher une information, préparer une réponse, parfois agir dans un outil. Laisser un modèle de langage choisir librement chaque étape fonctionne en démonstration, mais pose trois problèmes en entreprise : on ne sait pas toujours pourquoi il a fait un choix, il peut sortir du périmètre prévu, et une erreur peut avoir des conséquences réelles (un e-mail envoyé, une commande passée).

La réponse n’est pas de renoncer aux agents, mais de les encadrer. C’est ce que nous appelons le harnais : tout ce qu’on construit autour du modèle pour qu’il reste utile et prévisible.

LangGraph : écrire le chemin plutôt que l’espérer

LangGraph est une bibliothèque open source de l’écosystème LangChain. Elle décrit un agent comme un graphe :

  • un état partagé (la demande, les documents trouvés, le brouillon, la décision) ;
  • des nœuds, chacun responsable d’une étape (rédiger, vérifier, valider, envoyer) ;
  • des arêtes qui fixent l’ordre, y compris des arêtes conditionnelles quand plusieurs suites sont possibles.

Le modèle reste libre à l’intérieur d’une étape, mais c’est vous qui décidez de l’enchaînement. On peut relire le graphe, le tester, et savoir à tout moment où en est l’agent.

L’interruption : le moment où l’humain décide

LangGraph sait mettre un graphe en pause avec la fonction interrupt(). L’état est sauvegardé par un checkpointer, l’agent attend, et il reprend exactement au même endroit quand une personne a répondu. C’est la brique qui permet la validation humaine des actions sensibles.

Voici un exemple volontairement court : l’agent prépare une réponse à un client, mais ne l’envoie qu’après accord.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command

class Etat(TypedDict):
    demande: str
    brouillon: str
    decision: str

def rediger(etat: Etat):
    # Appel au modèle : il prépare, il n'envoie rien.
    reponse = modele.invoke(f"Prépare une réponse à : {etat['demande']}")
    return {"brouillon": reponse.content}

def valider(etat: Etat):
    # Le graphe s'arrête ici et attend une personne.
    decision = interrupt({"brouillon": etat["brouillon"]})
    return {"decision": decision}

def envoyer(etat: Etat):
    if etat["decision"] == "ok":
        outil_envoi(etat["brouillon"])  # seul outil autorisé
    return {}

graphe = StateGraph(Etat)
graphe.add_node("rediger", rediger)
graphe.add_node("valider", valider)
graphe.add_node("envoyer", envoyer)
graphe.add_edge(START, "rediger")
graphe.add_edge("rediger", "valider")
graphe.add_edge("valider", "envoyer")
graphe.add_edge("envoyer", END)
agent = graphe.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "demande-42"}}
# Premier appel : le graphe s'arrête sur interrupt()
agent.invoke({"demande": "Délai de livraison pour Sfax ?"}, config)
# Après accord de la personne : il reprend au même endroit
agent.invoke(Command(resume="ok"), config)

En production, on remplace InMemorySaver par un stockage durable (une base Postgres par exemple), pour qu’une validation puisse arriver une heure plus tard sans rien perdre. Le thread_id relie la reprise à la bonne demande.

Les autres pièces du harnais

Des outils limités au strict nécessaire

Un agent ne doit avoir accès qu’aux outils et aux données dont il a besoin, avec les droits les plus faibles possibles : lecture seule quand c’est suffisant, un seul destinataire autorisé, un plafond sur les montants. C’est la première défense contre une injection de prompt.

Des garde-fous à l’entrée et à la sortie

Filtres sur ce qui entre (données personnelles, instructions cachées dans un document) et contrôles sur ce qui sort (format attendu, règles métier, ton). Une sortie non conforme ne passe pas à l’étape suivante.

Des traces lisibles

Chaque étape est journalisée : ce que l’agent a reçu, ce qu’il a produit, quel outil il a appelé. On peut rejouer un cas, comprendre une erreur et l’expliquer à un client ou à un auditeur.

Une évaluation avant chaque mise en ligne

Avant de brancher l’IA, on constitue un jeu de cas de référence, et on garde une partie de ce jeu gelée, qui ne sert jamais à corriger. On mesure avant et après chaque changement de modèle ou de prompt. Sans cela, on croit progresser alors qu’on a seulement appris les réponses du test.

Par où commencer

  1. Choisir un processus court

    Une tâche répétitive, bien comprise, où une erreur est rattrapable : trier des demandes, préparer un brouillon, extraire des champs.

  2. Dessiner le graphe sur papier

    Les étapes, les décisions, et les points où une personne doit valider.

  3. Mesurer

    Un jeu de cas réels, un chiffre de départ, un seuil à atteindre avant de passer en production.

  4. Étendre prudemment

    On retire une validation humaine seulement quand les mesures montrent que l’agent est fiable sur cette étape.
